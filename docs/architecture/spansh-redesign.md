# Архитектура перехода на Spansh API

## Цель и границы

Убрать локальную галактическую БД, её первичный импорт, недельное обновление и HTML-скрейпинг EDSM. Приложение остаётся небольшим Rust CLI: получает исходную систему, формирует поиск небесных тел вокруг её координат на стороне Spansh, применяет критерии, группирует совпадения по родительским системам и выводит результат. Локальное постоянное хранилище не требуется.

## Текущее состояние (аудит main)

- Проект — CLI `ed_planet_search`, Rust 2024.
- Точка входа — `src/main.rs`, модули — в `src/parser/`; используется стандартный Cargo layout.
- `parser/search.rs` строит HTML URL EDSM и разбирает таблицы через scraper.
- `parser/planet.rs` делает отдельный HTML-запрос на каждое тело.
- Главный цикл запускает до 10 параллельных запросов к страницам тел и отбрасывает ошибки парсинга через `.ok()`.
- Есть несоответствие: CLI разбирает диапазоны температуры и давления, но параметры поиска передаёт только gravity; температура/давление фильтруются после загрузки HTML.
- Уникальность сейчас определяется по имени тела, а не по устойчивому ID64.
- Нет тестов, конфигурации таймаутов, общего ограничения частоты запросов и структурированного слоя ошибок.

## Целевая архитектура

```text
CLI / Args
  -> SearchUseCase
      -> SystemResolver (Spansh system name autocomplete/search)
          -> ResolvedSystem { id64, canonical_name, x, y, z }
      -> BodySearchQuery (criteria + reference_coords + radius)
      -> SpanshClient (HTTP, timeout, bounded concurrency, retry)
          -> POST /api/bodies/search (endpoint contract under verification)
          -> recall pages if API returns a search reference
      -> BodyNormalizer
      -> CriteriaEvaluator (defensive local validation)
      -> GroupBySystemId64
  -> CLI formatter
```

### Компоненты

1. **domain** — типы критериев, диапазоны, система, тело, результат. ID64 хранить как `u64`/строку, никогда как `f64`.
2. **spansh::client** — единственная точка HTTP-доступа. Базовый URL конфигурируемый для тестов; таймауты; лимит параллелизма; ограниченные повторы для сетевых ошибок, 429 и 5xx; не повторять постоянные 4xx.
3. **system_resolver** — разрешает полное имя системы в координаты и ID64. Правило выбора кандидата должно быть детерминированным; неоднозначность и fallback по компонентам имени покрыть отдельными тестами.
4. **query_builder** — строит payload Spansh из критериев и reference_coords. Не смешивает координаты центральной системы с фильтрами тела.
5. **pagination** — обходит все страницы до подтверждённого конца или заданного пользователем лимита; учитывает search_reference/recall, если именно такой контракт вернёт API.
6. **normalizer/evaluator** — приводит nullable-поля к доменным типам и повторно проверяет точные границы локально, не доверяя серверной фильтрации без проверки.
7. **presentation** — форматирует найденные тела и родительские системы; не содержит HTTP и бизнес-логики.

## Контракт Spansh: подтверждённое и требующее проверки

Из предварительного исследования сторонних клиентов известны кандидаты:
- `GET /api/systems/field_values/system_names?q=...`
- `GET /api/search/systems?q=...`
- `POST /api/bodies/search`
- `GET /api/bodies/search/recall/{reference}/{page}`
- `GET /api/system/{id64}`, `GET /api/body/{id64}`

Предварительный payload body search использует `filters`, `sort`, `size`, `page`, `reference_coords`. Для расстояния встречается форма `{ "min": 0, "max": 50 }`; другие фильтры имеют разные типы схем. Это пока не считается зафиксированным официальным контрактом: документация Spansh неполна, а живой POST-эксперимент ещё не проведён.

До включения полноценного поиска необходимо проверить:
- рабочий endpoint: прямой POST или POST `/save` + recall;
- фактическую форму запроса и ответа;
- точную семантику distance относительно reference_coords;
- поля ID64, координат системы, subtype и pagination;
- размер страницы, число страниц и поведение count/total;
- поведение при пустом результате, 400, 429, 5xx и обрыве соединения.

## Поток запроса

1. Валидировать аргументы CLI и диапазоны (finite, min <= max).
2. Разрешить имя центральной системы и получить точные координаты.
3. Сформировать body search с координатами и радиусом.
4. Получить все страницы, пока серверный контракт подтверждает наличие следующей страницы.
5. Нормализовать каждое тело, дедуплицировать по `body_id64` (fallback только если ID отсутствует — составной ключ).
6. Проверить радиус и пользовательские критерии локально.
7. Группировать по `system_id64`, сортировать системы по расстоянию, тела — по имени/ID.
8. Остановиться после набора требуемого количества совпадений только если семантика сортировки и пагинации гарантирует корректность; иначе дочитать страницы.

## Отказы и эксплуатация

- Не хранить dump и не запускать background importer.
- Все запросы имеют connect/overall timeout.
- По умолчанию один-два одновременных запроса и мягкий интервал между запросами; настройки не должны создавать burst.
- Повторять только временные ошибки с экспоненциальной задержкой и jitter; ограниченное число попыток.
- Не скрывать ошибки нормализации/сетевого запроса через `.ok()`; считать и сообщать частичные ошибки.
- Кэширование в памяти допустимо только как оптимизация на время одного процесса; correctness не должна от него зависеть.
- Spansh — внешний источник: отсутствие/устаревание данных должно быть отражено в документации и сообщениях.

## Этапы реализации

1. Зафиксировать базовую ветку и привести Cargo target к реальному layout.
2. Добавить HTTP transport и контрактные DTO без преждевременного закрепления непроверенной схемы.
3. Получить реальные JSON fixtures с живого Spansh и зафиксировать их в tests/fixtures.
4. Реализовать resolver и body search builder по подтверждённым fixtures.
5. Реализовать пагинацию, нормализацию, фильтры и группировку.
6. Переключить CLI с EDSM HTML на Spansh; удалить scraper/futures/indicatif и старые модули после эквивалентной функциональности.
7. Добавить CI: unit + integration fixture tests; сетевые smoke tests — отдельно, вручную/по расписанию, не блокируют обычный CI.

## Критерии готовности

- Нет локальной базы, импорта, cron/background refresh или EDSM HTML scraping.
- Поиск использует координаты центральной системы и радиус.
- Результаты содержат тела из соседних систем, не только из центральной.
- Все критерии пользователя применяются корректно, включая температуру, давление, гравитацию, landable и mapped status (если поле реально доступно).
- Пагинация не теряет результаты и дедупликация устойчива к одинаковым именам.
- Ошибки Spansh не превращаются в ложный «0 результатов».
- Unit и fixture integration tests проходят без сети.
