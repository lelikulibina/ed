# План восстановления парсера EDSM

## Цель
Вернуть предсказуемую работу поиска планет, не маскируя сетевые блокировки под пустую выдачу и не пытаясь обходить CAPTCHA/Cloudflare Challenge.

## Что установлено
- Поиск и карточки планет загружаются HTML-запросами через один `reqwest::Client`.
- `fetch_html` не проверяет HTTP-статус и тип содержимого; HTML challenge с кодом 200 передаётся парсеру как обычная страница.
- `main.rs` превращает все ошибки загрузки планет в `None` через `.ok()`.
- Пустая выдача поиска завершает пагинацию, поэтому важно отличать штатную страницу EDSM от страницы защиты.
- EDSM документирует API получения тел конкретной системы (`/api-system-v1/bodies`), но этот endpoint сам по себе не заменяет используемый приложением поиск планет по радиусу/сектору и его фильтры. Полный переход на API требует отдельной реализации обхода систем и проверки ограничений API. Поэтому текущий этап не будет делать неподтверждённую замену алгоритма.

## Решение
Сохранить существующий пользовательский сценарий и сначала стабилизировать текущий HTML-поток:
1. Централизовать настройки HTTP-клиента: явные connect/request timeouts и идентифицирующий User-Agent приложения.
2. Проверять ответ до передачи в `scraper`: Cloudflare challenge, HTTP status и Content-Type.
3. Возвращать информативные ошибки с URL и причиной; не преобразовывать блокировки в пустой результат.
4. Не подавлять ошибки загрузки карточек планет в CLI.
5. Покрыть детектор challenge и разбор числовых значений unit-тестами.
6. Сохранить лимит параллелизма и текущие фильтры поиска.

## Границы
- Не обходить CAPTCHA, browser challenge, rate limit или другие механизмы контроля доступа.
- Не добавлять случайную ротацию User-Agent, прокси или имитацию браузера.
- Не менять критерии поиска и формат CLI без необходимости.
- API-first/альтернативный источник оставить отдельным следующим этапом после проверки, что он покрывает географический поиск и все необходимые поля.

## Критерии приёмки
- HTTP 403/429/5xx не интерпретируются как валидная HTML-страница.
- Challenge-страница, даже с HTTP 200, распознаётся и выдаёт понятную ошибку.
- Некорректный Content-Type не передаётся HTML-парсеру.
- Ошибки загрузки планет видны пользователю в stderr, а не исчезают бесследно.
- Нормальная HTML-страница продолжает обрабатываться прежним алгоритмом.
- Изменения находятся только в `fix/cloudflare-resilience`.
