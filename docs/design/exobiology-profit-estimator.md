# Проектирование прогноза экзобиологической прибыли

Дата: 2026-11-20  
Ветка: `refactor/spansh-api-architecture`

## Цель

Для каждой найденной планеты показывать оценку возможной выручки от полного сбора экзобиологических образцов. На первом этапе — прогноз по характеристикам планеты и справочнику видов; после получения биологических сигналов — уточнённый прогноз; после фактического сбора — подтверждённую сумму.

Это отдельная функция поверх поиска планет. Текущие критерии поиска и поведение фильтра Water не меняются.

## Источники и правила игры

Основной справочник цен и условий:
- Русская статья «Экзобиолог»: https://elite-dangerous.fandom.com/ru/wiki/Экзобиолог
- Таблица стоимости: https://elite-dangerous.fandom.com/ru/wiki/Экзобиолог/Стоимость_образцов
- Англоязычная таблица условий и colony range: https://elite-dangerous.fandom.com/wiki/Exobiology_Sample_Values_and_Details

Для полного набора из трёх образцов используется фиксированная стоимость вида. Бонус First Logged / первое занесение даёт итоговый множитель x5 к базовой выплате. Это условный сценарий: по одним лишь параметрам тела нельзя гарантировать получение бонуса. First Footfall — важный признак, но сам по себе не должен трактоваться как безусловная гарантия бонуса.

Видовая таблица содержит ограничения по:
- subtype / типу планеты;
- атмосфере (включая отдельные Water и Water-rich);
- температуре поверхности в K;
- гравитации;
- давлению;
- типу вулканизма;
- классу звезды / условиям биологическая группаительской системы;
- дополнительным условиям системы и тела.

Часть условий не указана для некоторых видов и трактуется как отсутствие ограничения только если это явно следует из справочника. Неизвестное значение параметра не равно «подходит»: кандидат помечается как требующий проверки.

## Подтверждённый контракт Spansh

Схемы Spansh в репозитории [elite_dangerous_schemas](https://github.com/spansh/elite_dangerous_schemas) проверены на commit `9355a09c054ebf0975a1e662a62dec46b303e990`:

- [api.openapi.json](https://github.com/spansh/elite_dangerous_schemas/blob/9355a09c054ebf0975a1e662a62dec46b303e990/api.openapi.json): `GET /body/{id64}` возвращает объект `{ "record": SearchBody }`.
- [model.openapi.json](https://github.com/spansh/elite_dangerous_schemas/blob/9355a09c054ebf0975a1e662a62dec46b303e990/model.openapi.json): `SearchBody` содержит `volcanism_type`, `signals: [{name,count}]`, `signal_count`, `signals_updated_at`, `genuses: [{name}]` и `landmarks`.
- В SearchBody биологические сигналы представлены записью `signals[].name == "Biological"`; `signal_count` — общее число сигналов и не заменяет биологический count.
- Dump-модель `Body` использует camelCase: `volcanismType` и вложенный объект `signals` с картой `signals`, массивом Codex-токенов `genuses` и `updateTime`. Биологический count хранится под ключом `$SAA_SignalType_Biological;`.
- Официальное значение отсутствия вулканизма — `No volcanism`. Если поле `volcanism_type` отсутствует, приложение оставляет его неизвестным, а не выводит отсутствие вулканизма автоматически.
- В этих моделях нет прямых полей First Footfall или First Logged. SearchBody содержит `updated_at`, dump Body — `updateTime`; это дата последнего обновления записи тела, а не дата высадки и не подтверждение First Footfall. `is_mapped`, `landmarks` и отсутствие биосигналов не являются заменой этим статусам.
- `parents` позволяют восстановить биологическая группаительскую цепочку, но для правил по звезде может потребоваться загрузить тела системы из dump и связать их по ID64.

Парсер `Body::from_json` поддерживает SearchBody и dump Body. Для genus names и Codex-токенов нормализуются известные соответствия, в частности Bacterial → Bacterium, Cactoids → Cactoida, Fumerolas → Fumerola, Tussocks → Tussock.

Текущий JSON-справочник содержит 76 записей по 14 биологической группым. Это расширенный профильный набор, но не полный список всех известных видов. Для правил с обязательным рельефом/фумаролами отсутствие terrain в SearchBody не трактуется как совпадение: кандидат помечается как требующий проверки. Geological signal count исключает Fumerola при известном нуле, но положительное значение само по себе не подтверждает нужную фумаролу. Температурные условия могут быть общими или зависеть от атмосферы; для этого справочник поддерживает `conditional_temperature_rules`.

## Три уровня оценки

### 1. Предварительный прогноз (FSS / параметры тела)

Сопоставлять известные параметры тела с правилами видов. Выводить:
- список возможных биологических групп;
- виды-кандидаты внутри биологической группы;
- базовую минимальную и максимальную выручку;
- сценарий First Logged x5;
- перечень неизвестных параметров, которые мешают уточнить оценку.

Нельзя показывать сумму как гарантированную. Если нет данных о биосигналах, это только кандидатный прогноз.

### 2. Уточнённый прогноз (после DSS / biological signals)

Наличие biological signals и число сигналов ограничивают множество возможных биологических групп. Внутри каждого биологической группы может быть только один вид на конкретном теле, поэтому нельзя складывать выплаты всех вариантов вида одного биологической группы. Для каждого биологической группы:
- множество видов-кандидатов;
- минимальная/максимальная стоимость;
- ожидаемая стоимость только при наличии обоснованных вероятностей.

Сумма по планете — сумма по подтверждённым биологической группым, с одним видом на биологическая группа. Если вид пока неизвестен, показывать диапазон, а не складывать все варианты.

### 3. Подтверждённая стоимость

После обнаружения/сбора конкретных видов прогноз заменяется точной суммой. Учитываются фактические статусы сбора и First Logged, если эти сведения доступны из игрового журнала/данных пользователя.

## Математика

Пусть для биологической группы g доступен набор возможных видов S_g, у каждого вида базовая стоимость V_s.

- Нижняя граница биологической группы: min(V_s), если вид не определён.
- Верхняя граница биологической группы: max(V_s).
- Если вид определён: V_s.
- Прогноз по планете: сумма границ/ожиданий по биологической группым, но не по всем видам сразу.

Ожидаемая стоимость вида внутри биологической группы:
`E_g = sum(p_s * V_s)`, где `sum(p_s)=1`.

Вероятности `p_s` нельзя выдумывать или считать равномерными без оснований. Их следует получить из статистики наблюдений (например, Spansh Exomastery / подтверждённые записи EDDN) и откалибровать на независимой выборке. Пока такого набора данных нет, интерфейс должен показывать диапазон и пометку «вероятность не рассчитана».

First Logged сценарий:
- обычная оценка: `E_base`;
- потенциальный бонусный сценарий: `5 * E_base`;
- не применять x5 автоматически ко всем планетам; выводить его отдельно как «если доступен First Logged».

First Footfall и First Logged — разные статусы. First Footfall относится ко всему телу, First Logged — к конкретному биологическому виду на теле и определяется первым завершённым/сданным набором образцов. Поэтому First Footfall используется только как ориентир, а ×5 остаётся условным сценарием.

Spansh не отдаёт прямой статус First Footfall или First Logged. Программа работает независимо от Elite Dangerous и не читает игровые журналы. Поля `signals` с записью `Biological` и список `genuses` подтверждают, что биологические сигналы/биологические группы зарегистрированы в данных Spansh, но сами по себе не доказывают высадку: обнаружение биосигналов возможно с орбиты. Поэтому эти поля нельзя использовать как статус First Footfall. Дата `updated_at` / `updateTime` также является датой обновления записи, а не датой высадки; прежняя эвристика по порогу 2022 года удалена.
## Необходимые данные в модели

Текущий `Body` уже хранит subtype, atmosphere, temperature (K), pressure, gravity, landability, mapped state, дату последнего обновления записи Spansh, volcanism_type, biological/geological signal count, genus list и signals update time. Контракт полей вулканизма и биологии подтверждён официальными схемами Spansh и реализован в парсере.

Для следующих этапов остаются:
- body star/system context: восстановление primary star class и признаков требуемых соседних тел по parents и system dump;
- first_footfall / First Logged: прямые флаги отсутствуют в Spansh-модели; биологические сигналы и genuses не доказывают высадку; для достоверного статуса нужен отдельный источник;
- landmarks / подтверждённые виды: использовать subtype из landmarks только как свидетельство уже известного вида, не как First Logged;
- сведения о фактических сборах и бонусах из независимого источника данных, если такой будет найден.

Не предполагать имена полей по догадке. Любые новые поля сначала подтверждать схемой или реальным fixture.

## Источник вероятностей и качество прогноза

Статья Fandom даёт правила и цены, но не даёт вероятности появления конкретного вида. Поэтому для численного математического ожидания нужен отдельный датасет наблюдений. Потенциальные источники:
- Spansh Exomastery exports / dumps;
- EDDN sightings с характеристиками тела;
- EDSM body records для параметров, отсутствующих в основном поисковом ответе.

Не использовать статистику EDEXO как скрытую зависимость без отдельной оценки лицензии/доступности и воспроизводимости. Его описание подтверждает сам подход: правила + наблюдения + калибровка вероятностей, но проект не является источником, который автоматически можно встроить в наш код.

Вероятности калибровать по фактическим наблюдениям и проверять на hold-out наборе. Если датасет не подключён, не называть диапазон «ожидаемой прибылью» в строгом статистическом смысле — использовать «потенциальная стоимость» / «оценка диапазона».

## Будущий консольный UI

Не менять текущий CLI-контракт сразу. Следующим этапом можно добавить интерактивный режим, сохранив существующие флаги для автоматизации.

Предлагаемая структура меню:
1. Поиск планет по физическим критериям.
2. Поиск планет по потенциальной экзобиологической прибыли.
3. Просмотр найденных планет и подробностей прогноза.
4. Настройка профилей поиска.
5. Выход.

В режиме экзобиологии фильтры планеты (тип, атмосфера, температура, давление, гравитация, вулканизм) должны быть отдельны от сортировки по стоимости. Пользователь сможет задавать минимальную потенциальную стоимость, число видов/биологических групп и режим бонуса First Logged.

## Принципиальные ограничения

- Не обещать точную прибыль по одним лишь физическим параметрам.
- Не суммировать все виды внутри одного биологической группы.
- Не применять x5 как гарантированный множитель.
- Не путать First Footfall и First Logged.
- Не считать отсутствие сигнала в неполных данных доказательством отсутствия биологии.
- Не ослаблять существующие критерии поиска планет ради повышения прогнозируемой стоимости.
