# План реализации единого TUI

Спецификация: `docs/superpowers/specs/2026-11-21-unified-terminal-ui-design.md`
Рабочая ветка: `feature/interactive-terminal-ui`

## Границы

Не менять алгоритм отбора тел, семантику критериев, Spansh parsing и семь пресетов. Удалить только старый пользовательский рендеринг результатов и связать приложение с Ratatui.

## Задача 1. Общая конфигурация поиска и тесты

Файлы: `src/application/config.rs`, `src/application/mod.rs`, тесты.

- Создать `SearchConfig` с центральной системой, `SearchCriteria` и источником/меткой конфигурации.
- Вынести фабрику конфигурации из значений TUI и CLI; проверять непустую систему и count > 0.
- Для ручной формы валидировать диапазоны и список типов поверхности; пустой список не должен незаметно становиться any, только явное `any`.
- Профиль №3 формирует оба типа поверхности как OR.
- Сначала написать тесты на валидную/невалидную конфигурацию, count, OR, независимый bio-флаг; убедиться, что тесты падают, затем реализовать.

## Задача 2. События и прогресс прикладного поиска

Файлы: `src/application/search.rs`, `src/spansh/bodies.rs`, при необходимости новые типы событий.

- Добавить типизированные события: ResolvingSystem, CenterResolved, Searching, PageLoaded, Completed, Failed.
- Сохранить существующие публичные методы либо адаптировать их через внутренний метод с необязательным отправителем событий.
- События страниц не должны менять правила дедупликации, локальной фильтрации, лимиты или пагинацию.
- Тестами проверить последовательность событий на локальном HTTP fixture/server и неизменность результатов.

## Задача 3. Единый TUI state machine и неблокирующий запуск

Файлы: `src/presentation/tui.rs`, новые модули состояния по необходимости.

- Состояния: Configure, Searching, Results, Error.
- Единая оболочка и focus model для областей навигации, формы и результатов.
- Запуск поиска в Tokio-задаче, события через канал; event loop TUI не блокируется.
- При CLI-конфигурации пропустить Configure и стартовать Searching; после Completed сразу показать Results.
- При интерактивном сценарии Configure → Searching → Results.
- Обработать отмену/повтор, возврат к критериям, пустой список, ошибки и terminal cleanup.
- Написать тесты переходов state machine до реализации обработчиков.

## Задача 4. Интерактивное представление результатов

Файлы: `src/presentation/tui.rs`, `src/presentation/output.rs` (удаление старого renderer после переноса нужных вычислений), модуль presentation для форматирования.

- Список планет с выделением и навигацией.
- Панель подробностей выбранной планеты: системные и физические параметры, биологические/геологические сигналы, группы, доступный расчёт кандидатов экзобиологии.
- Сохранить русские названия групп и предупреждения о неполноте справочника.
- Пустой результат и отсутствие данных показывать явно, не подменяя неизвестные значения нулями.
- Тесты форматирования и выбора строки.

## Задача 5. Единая точка входа и удаление старого вывода

Файлы: `src/main.rs`, `src/cli.rs`, модули presentation.

- Без аргументов открыть Configure.
- С аргументами поиска собрать SearchConfig, выполнить поиск и показать тот же TUI в Results.
- `--help` / `--version` оставить Clap-режимами.
- Удалить вызов `print_results` и старый println-поток пользовательских результатов.
- Если TUI невозможен из-за отсутствия терминала, вывести понятную ошибку вместо fallback в старый текстовый формат.
- Тесты парсинга аргументов и сценариев входа.

## Задача 6. Полная проверка и ревизия

- `cargo fmt -- --check`
- `cargo clippy --locked --all-targets --all-features -- -D warnings`
- `cargo test --locked --all-targets`
- Проверить CI на последнем коммите этой ветки.
- Ревью изменений на регрессии критериев, OR-семантики, bio exclusion, terminal cleanup и отсутствия блокировки UI.
- Не заявлять о визуальной проверке на реальном терминале, если она не была выполнена.
